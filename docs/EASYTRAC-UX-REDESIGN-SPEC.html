UX Architecture Spec · v1 approved · amendments applied

Redesigning EasyTrac from a tool into a product.

Studied against Stape's information architecture, navigation, dashboard model, onboarding and status design — then rebuilt around one idea: people don't think in GTM containers, they think in "is my store's tracking working" — while keeping GTM reachable for the pros via progressive disclosure. v1 approved; the P0 build plan is now in progress (§11).

19,850 lines in one tool.html 1,049 inline style attrs 8 media queries total 5 / 10 nav items are "Soon" 3 heroes on one screen

The one problem underneath all the others

The current app names itself after its plumbing. The sidebar reads Pixel Config, GTM Container, Managed sGTM, Versions, Deployments, Audit — these are implementation stages, not things a merchant wants. A Salla store owner has exactly two questions: "is my tracking set up?" and "is my ad data accurate right now?" Nothing in the nav answers either directly.

Stripe never makes you think about idempotency keys to see whether you got paid — but the full developer surface is always there when you reach for it. That's the model: reorganize around the merchant's objects (Store → Destinations → Data) as the default, and keep the GTM machinery visible under an "Operations" group that a user opens when they want to go deeper. Outcomes for merchants, full control for pros — progressive disclosure, not two products.

Guiding constraints (yours — kept literally)

Reduce cognitive load · never show everything at once · progressive disclosure · one primary action per page · clear success/failure on every action · every page states system status immediately · onboarding under 5 minutes.

01 · Diagnosis

Full UI/UX audit

Every dimension you listed, graded against Stape. Each card: what Stape does better, what EasyTrac does worse today, and the move that lets us surpass them. Severity reflects impact on the merchant's ability to succeed.

01 · Information architectureThe nav exposes plumbing, not outcomes
◆ Stape better

Top level is objects a user owns: Containers, Gateways, power-ups. Machinery (Cloud Run, LBs) is never named. You navigate by what you have, not how it's built.

✕ EasyTrac worse

Sidebar mixes 4 overlapping models — Pixel Config, GTM Container, Managed sGTM, My Projects — with no clue which to use. "Container" and "Config" are the same job at different stages.

▲ How we surpass

Collapse to a single spine: Store → Destinations → Data. GTM/sGTM/versions/deployments become one "Infrastructure" drawer, opened only by power users.

02 · Navigation hierarchyHalf the navigation is dead
◆ Stape better

Every nav entry leads somewhere real. Unbuilt/premium capability appears contextually as an upsell inside the relevant screen, not as a permanently greyed peer.

✕ EasyTrac worse

5 of 10 items carry a "Soon" badge (Managed sGTM, Versions, Deployments, Health, Audit). The user scans a menu that's 50% broken promises — pure cognitive load and eroded trust.

▲ How we surpass

Ship 4 real destinations. Roadmap items live in a separate "Coming soon" tray or unlock progressively as the store matures — never as inert nav.

03 · Dashboard / visual hierarchyThree heroes, zero system status
◆ Stape better

Dashboard opens with request volume, health, and logs — the answer to "is it working?" is the first thing you see. Summary before detail.

✕ EasyTrac worse

Overview stacks a profile card + a marketing hero ("Setup pixels in minutes not hours") + Active Pixels + a Bento "Setup Summary." A marketing hero inside the app is the wrong altitude, and there are two competing primary CTAs.

▲ How we surpass

A tracking command center: health headline ("Your tracking is healthy · 1,204 events today · 0 issues"), connected destinations, and a recent-activity feed — the four tracking questions, always. One state-driven primary action. Kill the in-app marketing hero; never a generic SaaS dashboard.

04 · Onboarding / first-runNo guided first 5 minutes
◆ Stape better

Free tier, no card, a Setup Assistant and Tracking Checker that walk you from zero to a live container with verification at the end.

✕ EasyTrac worse

New user lands on a dashboard for a store that has nothing yet, plus an "account under review" wall. Empty state is a marketing hero, not a first step. No verification that the first event actually fired.

▲ How we surpass

A 4-step guided run (Store → Platform → First destination → Verify live event) with a persistent checklist. Success = a real event appears. Target <5 min, provable.

05 · Provisioning / deployment progressThe most impressive moment is invisible
◆ Stape better

Container spin-up shows discrete states and lands on a clear "live" screen with the endpoint URL.

✕ EasyTrac worse

Real end-to-end automation (create GTM → deploy → wire transport) runs as fire-and-forget with a 5-dot stepper buried in a tab. The genuinely hard, valuable work reads as a spinner.

▲ How we surpass

A full-screen live provisioning theater: named steps streaming in real time, per-step success ticks, retry-on-fail per step, ending on "Container live + first event verified."

06 · Health visualization / status indicatorsThe headline promise is gated "Soon"
◆ Stape better

Ships Logs + Monitoring rules as everyday features — real request/response inspection and alerts.

✕ EasyTrac worse

There's a Health view (score ring + per-platform grid) but it's locked behind "Soon," and the app goes blind after provisioning. Your #1 sales promise ("24/7 monitoring + auto-fix") has no shipped surface.

▲ How we surpass

Make Data Health the second nav item and ship it first. Per-destination status, match-quality score, drift alerts, "last event N sec ago." This is the differentiator — treat it as core, not premium.

07 · Logs UXNo live event stream at all
◆ Stape better

Filterable logs by client, event name, status code — the tool people actually debug with, and a retention upsell ladder (3→10 days→export).

✕ EasyTrac worse

No request log exists. A merchant who suspects tracking broke has nothing to look at and must trust or churn.

▲ How we surpass

A live event inspector: streaming rows, filter by event/destination/status, click a row → full payload + which destinations accepted it. Retention tiers mirror Stape's ladder.

08 · Platform configuration UXEvents + credentials crammed into accordions inside a wizard tab
◆ Stape better

Each destination (Meta, TikTok…) is its own Gateway with a focused, single-platform setup — no-code, one thing at a time.

✕ EasyTrac worse

Per-platform events + credentials live in stacked accordions (pc-ss-accordions) under a sub-tab of Pixel Config. Everything is visible at once; nothing is focused.

▲ How we surpass

A Destination is a first-class object with its own detail page: Overview · Events · Credentials · Health · Logs as tabs. Add one at a time via a focused sheet.

09 · Empty & loading statesMarketing where guidance belongs; spinners where skeletons belong
◆ Stape better

Empty states point at the next action; loading uses structured placeholders so the layout doesn't jump.

✕ EasyTrac worse

Empty overview = a hero ad. "Active Pixels" simply doesn't render until data exists, so first-run is a void. ~89 loading/placeholder references but no consistent skeleton system.

▲ How we surpass

Every list gets a purposeful empty state (illustration + one CTA) and a matching skeleton. Empty = "here's your next step," never a billboard.

10 · Mobile responsivenessEffectively desktop-only
◆ Stape better

Fully responsive marketing + usable app on tablet/phone.

✕ EasyTrac worse

8 @media rules across 19,850 lines and 1,049 inline styles. The fixed sidebar + inline widths don't collapse. KSA merchants are mobile-first — this is a reach problem, not a polish problem.

▲ How we surpass

Rebuild in the existing Next.js + design-token scaffold, mobile-first: sidebar → bottom tab bar / drawer, cards reflow, wizard is single-column by default.

11 · Forms · error & success feedbackFeedback is ad-hoc, not systematic
◆ Stape better

Inline validation, explicit success confirmation, consistent toasts.

✕ EasyTrac worse

~39 scattered toast/alert references, no unified pattern. Credential fields (pixel IDs, tokens) lack inline validation, so a typo surfaces as a silent tracking failure days later.

▲ How we surpass

One feedback contract: inline validate on blur, optimistic action → toast that names the result ("Meta connected · test event received"), errors that say what to fix.

12 · Settings · search · tables · maintainabilitySettings in a modal; no search; one unsplittable file
◆ Stape better

Dedicated settings area, searchable tables, componentized UI that scales.

✕ EasyTrac worse

Settings is a toggleSettings() modal; only ~10 tables and no global search/filter; 1,049 inline styles make consistent change impossible. The Next.js rebuild target exists but is empty.

▲ How we surpass

Settings as a real sectioned page; ⌘K command palette + per-table filter; ship the token-based component library the scaffold is already set up for.

What's already right — protect it

Real end-to-end GTM automation (not a mockup) · Arabic-first + Salla/Zid native · Snapchat strength for KSA · a design-token + Next.js scaffold already in place. The redesign keeps EasyTrac's brand and these strengths — it only changes structure.

02 · Redesign

New information architecture

Shift from a stage-based model (config → container → deploy → monitor) to an object-based model. The user manipulates three nouns; everything else is infrastructure the system manages for them.

OBJECT 01
Store

The workspace. One per merchant site (Salla/Zid/custom). Holds brand, plan, team, and the connection to the CMS. The top-level switcher.

OBJECT 02
Destination

One ad/analytics endpoint: Meta CAPI, TikTok, Snapchat, GA4, Google Ads. First-class, with its own events, credentials, health and logs. This is where value lives.

OBJECT 03
Event stream

The live flow of tracked actions (purchase, add_to_cart…) fanning out to destinations. The thing Health and Logs read from — the proof it works.

GTM & the machinery move to "Operations" — visible, not hidden

The GTM container, the managed sGTM server, versions, deployments and the audit trail are not the top-level spine anymore — but they are not hidden either. They group under an expandable Operations section that stays visible to everyone, and they open on demand via progressive disclosure (§03). A store owner can ignore Operations; an agency or technical marketer expects GTM to be right there, and it is. The launch roadmap ("Soon" capabilities) also lives here, visible — not deleted. This is progressive disclosure by intent, growth and context, not by removal or a mode setting.

03 · Redesign

Progressive disclosure — one product, revealed by depth

There is no mode switch and no "two products." There is one continuous product. Technical capability isn't hidden behind a toggle — it surfaces where and when a user reaches for it: by opening Operations, expanding a "technical details" disclosure, or simply as their store matures. A merchant and an agency use the same screens; the agency just goes deeper.

MECHANISM 1
Reveal by intent

Depth appears when the user asks for it: opening the Operations section, clicking a destination's GTM tab, or a "Show technical details" expander on a card. Nothing is pre-committed for them.

MECHANISM 2
Reveal by growth

Capability unlocks as it becomes relevant: infrastructure detail appears once a container is live; version history appears after the first re-publish; export/alerts surface as volume grows.

MECHANISM 3
Reveal by context

When something needs attention, the relevant depth comes to the user — a drift banner links straight into the GTM container view — rather than living behind a persistent "advanced" wall.

Every technical surface has a default-collapsed disclosure — not a mode

Why disclosure beats a mode switch

A mode toggle forces users to self-classify up front and splits the product in two. Progressive disclosure keeps one path: the merchant sees outcomes, the agency reaches one level deeper on the same screen, and a growing merchant graduates naturally with no wall and no setting to discover. The wedge stays Arabic-first AND agency-credible — without ever feeling like two apps.

09 · Execution

Migration strategy — no rewrite, no downtime

The current tool.html stays fully operational in production the entire time. The Next.js app in frontend/ becomes the migration target, and clean app routes move across one at a time behind a route switch — a strangler-fig, not a big-bang rewrite.

Grounded in the real code — two things that make this cheap

1 · The split is at the app server, not the sGTM edge-router. tool.html is an SPA that server.js already serves for clean routes (/dashboard, /sign-in… → tool.html). The migration switch lives here (or a thin proxy in front): named routes go to Next.js, the rest fall through to tool.html. (The edge-router/ is unrelated — it proxies tenant tracking traffic {slug}.sgtm.easytrac.io → each customer's Cloud Run container, not the app UI.) 2 · Shared auth is free. Auth is Firebase ID tokens verified server-side; the browser holds the Firebase session. Same origin ⇒ both UIs share it automatically — no bridge to build.

You launch on the new Home + Health (the first-impression wins) while the deep, working machinery keeps running on tool.html until its replacement is proven at parity.
