01 · Architecture

Migration architecture

Two processes behind one origin. The app server owns the front door and decides, per request path, who renders.

Browser
app.easytrac.io
One origin ⇒ one Firebase Auth session, shared by both UIs.
→
Front door
server.js
Path in MIGRATED_ROUTES? → proxy to Next. Else → existing tool.html / /api/* logic.
⇄
New
Next.js (frontend/)
Renders /home. Calls back to /api/* with the user's ID token.
DECISION
Same origin, reverse-proxy

Next.js runs as a sidecar process; server.js proxies migrated paths to it. Keeps cookies/Firebase session shared and avoids CORS. (Alt: Next static export served as files — rejected: Home needs runtime data + SSR guard.)

DECISION
Backend unchanged

Next calls the same /api/managed/* and /api/v1/* endpoints tool.html uses. No new auth system, no data migration.

DECISION
Reversible per route

MIGRATED_ROUTES is a Set + env flag. Remove /home from it → instantly back to legacy. This is the rollback.

Deploy note — verify before building

Confirm how the app is hosted today (per memory: prod deploys the main of a separate public repo; Railway may force NIXPACKS and ignore the Dockerfile). The sidecar needs the host to run two processes (node server.js + next start) or a single container that boots both. PR-0 is a spike to confirm this. If two-process hosting is blocked, fallback is deploying Next as a separate service and proxying by absolute URL — same code path, different upstream.

02 · Architecture

The route switch

The seam already exists. server.js:4578-4581 maps clean SPA routes to tool.html via an APP_ROUTES set. The switch is one check before it:

// server.js — add near APP_ROUTES definition const MIGRATED_ROUTES = new Set( (process.env.MIGRATED_ROUTES || '/home').split(',').map(s => s.trim()) ); const NEXT_UPSTREAM = process.env.NEXT_UPSTREAM || 'http://127.0.0.1:3000'; // ── in the request handler, BEFORE the APP_ROUTES → tool.html block ── const _clean = urlPath.replace(/\/+$/, '') || '/'; if (MIGRATED_ROUTES.has(_clean) || _clean.startsWith('/_next')) { return proxyToNext(req, res, NEXT_UPSTREAM); // same-origin reverse proxy } // …existing APP_ROUTES / tool.html / /api logic continues unchanged…

proxyToNext is a ~20-line http.request pass-through (mirror the pattern already in edge-router/server.js:proxyTo — pipe method, headers, body, stream the response). /_next/* must proxy too so Next's assets load. /api/* is matched earlier in server.js and is untouched, so Home's data calls keep hitting the existing handlers.

Why this is the whole harness

Migrating a future route = add its path to MIGRATED_ROUTES and build the Next page. No router rewrite, no infra change. The strangler grows one entry at a time; tool.html shrinks only when a route is proven at parity.

03 · Architecture

Auth integration

No new auth. The browser already holds a Firebase Auth session for this origin; Next.js reuses it. The backend already verifies Authorization: Bearer <idToken> via firestoreService.verifyIdToken.

ConcernP0 approach
Client SDKInitialize Firebase Web SDK in Next with the same config tool.html uses (extract to a shared NEXT_PUBLIC_FIREBASE_* env). Same origin ⇒ onAuthStateChanged resolves the existing user with no re-login.
Token on API callsA fetcher wrapper calls auth.currentUser.getIdToken() and sets the Authorization header on every /api/* request — exactly what the backend expects.
Route guardClient-side guard in AppShell: if no user after auth init → redirect to the existing /sign-in (still served by tool.html). SSR stays unauthenticated-safe (renders skeleton, hydrates with user).
Not in P0Server-side session cookies / SSR-authenticated data fetching. Home fetches client-side after auth resolves — simplest correct path. Revisit if SEO/SSR-data needed later.
Spike input needed

Pull the exact Firebase client config + which auth persistence tool.html uses (local vs session) so Next matches it. If tool.html uses session persistence, Home must too, or the shared-session assumption breaks. PR-1 acceptance depends on confirming this.

Data contract

Honest inventory: what exists in server.js today vs. the two thin endpoints Home needs. No backend re-architecture — the "new" ones are read-only aggregators over data already in Firestore.

EndpointStatusReturns / to buildFeeds
GET /api/managed/healthexistsContainer/platform health (spec §health)HealthHeadline
GET /api/v1/metricsexistsEvent volume / metricsTrackingStatusRow
GET /api/managed/client/{id}existsClient + provisioning statusstore context, empty-state gating
GET /api/managed/serverexistsManaged server infoInfra disclosure (later)
GET /api/home/summarynew · thin BFFAggregate: {storeName, plan, destinations:[{id,name,status,lastEventAt}]}DestinationsStrip, header
GET /api/home/recent-eventsnew · thin BFFLast N events: {name, ts, destinations:[{id,ok,code}]}RecentActivityFeed

Both new endpoints live in server.js beside the existing /api/managed/* handlers, reuse the same Firebase-token auth and clientId-ownership check (server.js:2083 pattern), and read existing Firestore docs — they aggregate, they don't create schema. If event-level data isn't yet persisted per-destination, recent-events ships behind an empty-state (returns []) and the feed shows its "no events yet" state — no fake data.

Typed contract first

Define these as TypeScript types in lib/fetcher.ts up front so Home builds against the contract while the two BFF endpoints are implemented in parallel. React Query polls health + metrics every ~15s for the "live" feel.

Skeleton

Skeleton cards matching final layout — no spinner, no layout shift. Route-level loading.tsx + per-widget suspense.

No store/container yet → EmptyState: "Let's get your store tracking." One CTA → the existing legacy setup route (P0 doesn't rebuild onboarding). tracking-identity kept

STATE · healthy
Green

HealthHeadline "Your tracking is healthy", live activity, primary CTA = "View live events" (→ legacy events for now).

STATE · degraded/down
Banner

Banner crit at top: "GA4 stopped receiving events 3h ago." Primary CTA = "Fix <destination>" (→ legacy for now). Status in color + text.

STATE · error
Fetch failed

Card-level error with Retry — names what failed ("Couldn't load tracking health"), never a blank screen or raw stack.

STATE · signed-out
Redirect

Auth resolves to no user → redirect to legacy /sign-in. Skeleton shows until auth settles.

P0 rule honored: every action has success/failure feedback (toasts wired via the primitive), the page communicates system status immediately (health headline is the first paint after skeleton), and one primary action (PrimaryActionCard is the only Button pri).
